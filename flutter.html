How Dart actually runs

Dart is unusual in shipping two production compilers and a development-only JIT, and almost every performance claim Flutter makes traces back to that choice. Knowing which compiler is active explains hot reload, tree shaking, const, startup time and why release builds behave differently from debug builds.

Three execution modes

Dart execution pipelines
ModeWhereCompilerWhat you get
JIT (kernel + JIT)flutter run debug, dart runFront-end to kernel AST, then optimising JIT in the Dart VMHot reload, assertions on, dart:mirrors-free but dynamic; slower and larger
AOT (native)--release/--profile on mobile & desktop, dart compile exeWhole-program compilation to machine code + snapshotFast startup, no JIT warm-up, tree shaking, no hot reload, no dart:mirrors
JS / WasmFlutter web, plain web appsdart2js (or dart compile wasm → WasmGC)Whole-program optimisation, deferred loading, JS numeric semantics

Snapshots, and why startup is fast

Dart persists a compiled program as a snapshot: a serialised heap plus code. A kernel snapshot (.dill) is platform-independent AST used in JIT mode. An AOT snapshot contains machine code and pre-initialised objects, so a release Flutter app does not parse or compile Dart at launch — it maps the snapshot and runs. That is why a release build starts in tens of milliseconds while a debug build spends time in the front-end.

shell
# standalone Dart
dart compile exe bin/server.dart -o build/server   # AOT native executable
dart compile aot-snapshot bin/server.dart          # snapshot run by dartaotruntime
dart compile js -O4 web/main.dart                  # optimised JS
dart compile wasm web/main.dart                    # WasmGC

# Flutter build modes
flutter run                 # debug   : JIT, hot reload, asserts on, DevTools
flutter run --profile       # profile : AOT + tracing enabled, asserts off
flutter run --release       # release : AOT, asserts off, no observatory

Hot reload versus hot restart

Hot reload compiles only the changed libraries to kernel, sends the delta to the running VM, swaps the method bodies, and then rebuilds the widget tree from the root. State is preserved because the Element tree and every State object are untouched. It fails or degrades when the change cannot be expressed as a body swap:

  • changing a class's declared fields or type hierarchy;
  • changing const values used in already-canonicalised constants;
  • editing main() or top-level/static initialisers that already ran;
  • adding or changing generic type parameters, enums, or @immutable shapes;
  • native code, assets declared in pubspec.yaml, or plugin registration.

Hot restart throws away the isolate and starts main() again — still no full native rebuild, but all Dart state is lost. A full restart (stop/run) is needed for native changes.

Interview follow-up

“Why does hot reload keep my state?” The correct answer names the Element tree: widgets are recreated, Elements and their State objects are not. A candidate who says “Flutter caches the widgets” has the model backwards.

Tree shaking and why reflection is banned

AOT and dart2js are whole-program compilers: they compute the reachable set from main() and discard the rest, which is how a Flutter binary containing the entire Material library ships at a few megabytes. Runtime reflection would make reachability undecidable, so dart:mirrors is unavailable in AOT and in Flutter. The replacement is build-time code generation (Chapter 15): json_serializable, freezed, retrofit, injectable all exist because reflection does not.

Release-only behaviour

Tree shaking also removes icon glyphs (--no-tree-shake-icons disables it) and any code only reachable via string lookup. Code that works in debug and throws NoSuchMethodError in release is almost always dynamic dispatch on something the compiler proved dead.

Assertions, and the debug/release split

assert() statements are compiled out entirely in release. Large parts of Flutter's own error checking — debugCheckHasMaterial, layout assertions, the “setState called during build” error — live inside asserts. Two consequences interviewers probe for: a debug build is not a performance benchmark, and code with side effects inside an assert silently changes behaviour between modes.

dart
// Never do this: the increment vanishes in release.
assert(counter++ < 10);

// Idiomatic debug-only work
assert(() {
  debugPrint('cache size = ${_cache.length}');
  return true;
}());

// Compile-time mode detection
const bool isProduction = bool.fromEnvironment('dart.vm.product');
bool get isDebug {
  bool d = false;
  assert(() { d = true; return true; }());
  return d;
}

Types, inference & sound null safety

Dart's type system is sound with one deliberate escape hatch. Understanding where soundness holds — and precisely what dynamic, Object? and late cost you — separates people who fight the analyzer from people who use it.

The type hierarchy

Object? ← top type (everything, including null) / \ Object Null / \ \ num, String, ... \ | \ Never ←──────────────┘ bottom type (no values; type of a throw) dynamic = Object? with static checking switched off

Key facts an interviewer will test:

Object?
The top type. Assigning to it is always safe; reading requires a cast or pattern match.
dynamic
Not a type so much as a permission slip: same runtime representation as Object?, but every member access is unchecked and resolved at runtime. Errors move from compile time to production.
Never
The bottom type. A function returning Never never returns normally, which lets the analyzer treat a call to it as unreachable — this is how throw can appear in an expression position and how exhaustive switches type-check.
void
“Value exists but you must not use it.” Distinct from Never (no value at all) and from Null (exactly null).

Sound null safety, precisely

String and String? are different types; the nullable one is the union with Null. Soundness means the compiler can prove a non-nullable variable is never null, so it emits no null checks and Flutter's AOT output gets faster and smaller. It also means the guarantee must hold everywhere — hence the strict rules on initialisation.

dart
String? name;                 // defaults to null — legal
String  title;                // ERROR unless initialised before use

// 1. flow analysis (promotion)
void greet(String? n) {
  if (n == null) return;
  print(n.toUpperCase());     // promoted to String — no ! needed
}

// 2. promotion does NOT apply to fields, top-levels, or getters
class Box { String? v; }
void f(Box b) {
  if (b.v != null) {
    // print(b.v.length);     // ERROR: b.v could change between reads
    final v = b.v!;           // copy to a local, then use
    print(v.length);
  }
}

// 3. the null-aware family
final len   = name?.length;                 // null if name is null
final safe  = name ?? 'anonymous';          // default
name      ??= 'anonymous';                  // assign if null
final chars = name?.split('') ?? const [];  // chain + default
list?..add(1)..add(2);                      // null-aware cascade
final firstOrNull = list.isEmpty ? null : list.first;

late — three different jobs

  • Deferred non-null initialisation: late final Repo repo; assigned in initState. Reading before assignment throws LateInitializationError — a runtime check you opted into.
  • Lazy initialisation: late final x = expensive(); runs the initialiser on first read, once. Useful for costly fields and for fields that need this.
  • Breaking initialisation cycles: two objects that reference each other.
Cost

late without an initialiser adds a guard on every read and moves a compile-time error to runtime. late final with an initialiser is the good case; bare late fields in widgets are a common source of crashes after hot reload or when initState throws.

Inference rules worth memorising

  • var infers from the initialiser and is then fixed; final is the same plus immutable binding; const requires a compile-time constant.
  • An empty collection literal with no context infers List<dynamic> — annotate it: final ids = <int>[];.
  • Downward inference flows from the context type: final Map<String, int> m = {}; infers the literal's arguments.
  • Least-upper-bound inference on conditionals can widen unexpectedly: cond ? 1 : 'a' infers Object.
  • FutureOr<T> is the union Future<T> | T and is how APIs accept sync or async callbacks.
Interview follow-up

“Is Dart's generics covariance sound?” No — Dart chose covariant generics with runtime checks: List<int> is a subtype of List<num>, so writing a double into it must be caught at runtime. That check is the one place the static type system is deliberately incomplete. Chapter 07 covers the fix (Iterable read-only views, covariant keyword).

const, final & canonicalisation

In most languages const is a style preference. In Flutter it is a performance primitive with direct consequences for how many widgets rebuild, because canonicalised constants are identical and identity short-circuits the diffing algorithm.

The three levels of immutability

When fixedObject mutable?Stored where
var x = [1]neveryesheap, per assignment
final x = [1]binding fixed at runtimeyes — x.add(2) is legalheap, once per construction
const x = [1]compile timeno — deeply immutablecanonicalised constant pool

Canonicalisation

Two const expressions with equal type and equal arguments produce the same object. This is why identical(const Text('a'), const Text('a')) is true, and it is the mechanism behind the most-repeated Flutter performance advice.

dart
identical(const [1, 2], const [1, 2]);   // true  — same canonical object
identical([1, 2], [1, 2]);               // false — two heap allocations

class Point {
  final double x, y;
  const Point(this.x, this.y);           // const constructor: all fields final
}
const a = Point(1, 2);
const b = Point(1, 2);
assert(identical(a, b));                 // true

// const context: the inner const is implied
const grid = [Point(0, 0), Point(1, 1)];

// Not const: arguments are not compile-time constants
final p = Point(dx, dy);

Why Flutter cares

Element.updateChild begins with if (identical(newWidget, oldWidget)) return;. A const widget passed to the same position is the identical object, so the entire subtree beneath it is skipped — no build, no diffing, no layout. That is the whole story behind prefer_const_constructors.

dart · const as a rebuild barrier
// Rebuilds the icon and its render object work every frame:
Widget build(BuildContext context) => Column(children: [
  Icon(Icons.star, size: 32),
  ExpensiveHeader(),
]);

// Skipped entirely on rebuild — identical objects:
Widget build(BuildContext context) => Column(children: const [
  Icon(Icons.star, size: 32),
  ExpensiveHeader(),   // only if ExpensiveHeader has a const constructor
]);
Design rule

Give every one of your own widgets a const constructor. It costs one keyword and makes the widget usable as a rebuild barrier by every caller. freezed and the analyzer's prefer_const_constructors_in_immutables lint enforce it.

Limits

const cannot capture anything from the enclosing scope, so it is unavailable the moment a widget takes a runtime value, a callback closure, or a Theme.of(context) colour. Do not contort code to force const; hoist the constant parts into their own const widget instead.

Compile-time constant expressions

Legal in a const: literals, other constants, arithmetic and logic on them, string interpolation of constants, const constructor calls, collection literals with spread and if over constant conditions, and String.fromEnvironment. Illegal: anything reading a variable, a method call, DateTime.now(), [].length on a non-const list.

dart
const flavour = String.fromEnvironment('FLAVOUR', defaultValue: 'dev');
const enableX = bool.fromEnvironment('ENABLE_X');
const maxRetries = int.fromEnvironment('RETRIES', defaultValue: 3);

// dart-define feeds these:  flutter run --dart-define=FLAVOUR=prod
const endpoints = {
  'dev':  'https://dev.api.example.com',
  'prod': 'https://api.example.com',
};
const baseUrl = endpoints[flavour]; // legal: constant map, constant key

Functions, closures & callables

Functions are objects with a type, closures capture variables by reference, and any class can be made callable. Half of Flutter's API surface is a function type in a named parameter, so the details matter.

Parameters: four kinds, two syntaxes

dart
// required positional
int add(int a, int b) => a + b;

// optional positional, with defaults
String pad(String s, [int width = 8, String fill = ' ']) => s.padLeft(width, fill);

// named — optional by default, and order-independent at the call site
Widget box({double? width, double? height, Color color = Colors.black}) => ...;

// named + required (the Flutter idiom)
Future<User> fetch({required String id, Duration? timeout, bool cache = true});

fetch(id: 'u1', cache: false);

// function types
typedef Reducer<S, A> = S Function(S state, A action);
typedef AsyncGuard = Future<T> Function<T>(Future<T> Function() body); // generic fn type
void onEach(void Function(int index, String value) cb) {}
Rule

A parameter list cannot mix optional positional and named. Prefer named parameters for anything with more than two arguments or any boolean — Container(clipBehavior: Clip.hardEdge) reads; Container(true) does not. The avoid_positional_boolean_parameters lint encodes this.

Closures capture variables, not values

dart
// Each iteration of a for-in / for-var loop gets a fresh binding in Dart,
// so this prints 0 1 2 (unlike the classic JavaScript var trap).
final fns = <void Function()>[];
for (var i = 0; i < 3; i++) { fns.add(() => print(i)); }
for (final f in fns) f();   // 0 1 2

// But a captured mutable *variable outside* the loop is shared:
var total = 0;
final inc = () => total++;
inc(); inc();
print(total); // 2

// Counter factory — the canonical closure-as-state example
int Function() counter() {
  var n = 0;
  return () => ++n;
}
final next = counter();
next(); next(); // 2 — state lives in the closure, not in a field
Leak source

A closure captures its entire enclosing scope, including this. Passing () => setState(...) to a long-lived object (a stream, an animation, a global service) keeps the State, its BuildContext, and everything reachable from them alive. This is the number-one memory leak in Flutter apps; the fix is to cancel or remove the listener in dispose.

Callable classes and tear-offs

dart
// A class with `call` behaves as a function — used by use-case classes
class ValidateEmail {
  const ValidateEmail();
  bool call(String input) => RegExp(r'^[^@]+@[^@]+\.[^@]+$').hasMatch(input);
}
const validate = ValidateEmail();
validate('a@b.co');            // no .call needed
final f = validate.call;       // tear-off of the call method

// Method tear-offs — prefer over wrapping in a lambda
items.forEach(print);                  // not (x) => print(x)
final parse = int.parse;               // static tear-off
final upper = 'abc'.toUpperCase;       // bound instance tear-off
final ctor  = Point.new;               // constructor tear-off (Dart 2.15+)
final ints  = strings.map(int.parse).toList();
Interview follow-up

“Why do two identical closures compare unequal?” Because closure equality is identity unless the closures are tear-offs of the same method on the same receiver. That is exactly why passing an inline lambda as a widget callback defeats const and why removeListener fails if you pass a new lambda — you must keep a reference to the original.

Generic functions and type-argument inference

dart
T? firstWhereOrNull<T>(Iterable<T> xs, bool Function(T) test) {
  for (final x in xs) if (test(x)) return x;
  return null;
}

// Bounded type parameter + inference from the argument
R fold<T, R extends num>(Iterable<T> xs, R seed, R Function(R, T) f) {
  var acc = seed;
  for (final x in xs) acc = f(acc, x);
  return acc;
}

// A generic function *type* (rank-2) — note the type parameter on Function
final S = <T>(T v) => [v];
T Function<T>(T) identityFn = <T>(T v) => v;

Classes & initialisation order

Dart's constructor grammar is larger than most languages': generative, named, factory, redirecting, const, and an initialiser list that runs before the body. Initialisation order is a standing interview question because this is not available in the parts that run first.

The exact order

  1. Initialiser list of the most-derived constructor — left to right. this is not in scope here.
  2. Field initialisers declared inline (final x = 3;) — also without this.
  3. Superclass constructor, recursively through the same steps.
  4. Constructor body of the superclass, then down the chain to the most-derived body. this is fully available.
dart
class Animal {
  final String name;
  Animal(this.name) { print('Animal body: $name'); }
}

class Dog extends Animal {
  final int legs;
  final String tag;
  Dog(String name, {this.legs = 4})
      : tag = name.toUpperCase(),        // 1. initialiser list
        assert(legs >= 0),               //    asserts run here too
        super(name) {                    // 3. super — always last in the list
    print('Dog body: $tag / $legs');     // 4. body
  }
}
// Output: Animal body: rex  →  Dog body: REX / 4
Why this trips people up

Because the superclass body runs before the subclass body, calling an overridden method from a superclass constructor sees uninitialised subclass fields (null for nullable, or a LateInitializationError). Never call virtual methods from a constructor — do it in an init() the caller invokes, or in Flutter's initState.

Constructor forms

dart
class Temperature implements Comparable<Temperature> {
  final double celsius;

  // generative + const
  const Temperature(this.celsius);

  // named
  const Temperature.absoluteZero() : celsius = -273.15;

  // redirecting: delegates to another constructor of the same class
  const Temperature.freezing() : this(0);

  // factory: may return a cached/subclass/other instance, may be async-free only
  factory Temperature.fromFahrenheit(double f) => Temperature((f - 32) * 5 / 9);

  // factory used as a cache (the singleton/flyweight pattern)
  static final _cache = <double, Temperature>{};
  factory Temperature.cached(double c) => _cache.putIfAbsent(c, () => Temperature(c));

  // super parameters (Dart 2.17+): forwards without repeating the field
  @override int compareTo(Temperature other) => celsius.compareTo(other.celsius);
}

class Padded extends Temperature {
  final String label;
  const Padded(super.celsius, {required this.label});   // super.x forwarding
}
generative
Actually allocates. Can be const. Can use the initialiser list.
factory
Returns any instance of the declared type — a cache hit, a subclass, a parsed variant. Cannot be const, has no initialiser list, has no this.
redirecting
A.x() : this(...). Zero-cost aliasing; keeps const-ness.
redirecting factory
factory A() = B; — the declaration is the delegation, used heavily by freezed.

Getters, setters, static members, operators

dart
class Money {
  final int cents;
  const Money(this.cents);

  // computed getter — no storage, callers see a property
  double get dollars => cents / 100;
  bool get isZero => cents == 0;

  // setter (rare in immutable designs)
  set dollars(double v) => throw UnsupportedError('immutable');

  static const zero = Money(0);
  static Money sum(Iterable<Money> xs) => Money(xs.fold(0, (a, m) => a + m.cents));

  Money operator +(Money o) => Money(cents + o.cents);
  Money operator -(Money o) => Money(cents - o.cents);
  Money operator *(num k)   => Money((cents * k).round());
  bool  operator <(Money o) => cents < o.cents;
  Money operator -()        => Money(-cents);           // unary minus
  int   operator [](String k) => k == 'cents' ? cents : 0;

  @override bool operator ==(Object other) =>
      other is Money && other.cents == cents;
  @override int get hashCode => cents.hashCode;
  @override String toString() => '\$${dollars.toStringAsFixed(2)}';
}
Interview follow-up

“What must hold when you override ==?” Reflexive, symmetric, transitive, consistent, and a == b ⇒ a.hashCode == b.hashCode. Break the last one and your object silently vanishes from Set and Map. Use Object.hash(a, b, c) / Object.hashAll(list) rather than hand-rolled XOR, and prefer freezed or a record so you never write it by hand.

Inheritance, mixins & class modifiers

Dart has single inheritance, implicit interfaces, and mixins with a linearised resolution order. Dart 3 added modifiers (sealed, final, base, interface, mixin class) that let a library author state exactly how a type may be reused.

Three reuse mechanisms

ClauseInherits implementation?CountMust implement all members?
extendsyesoneno — only abstract ones
implementsnomanyyes — every member, including fields as getters/setters
with (mixin)yesmany, orderedno

Every class in Dart implicitly declares an interface, so implements SomeConcreteClass is legal and means “promise the same API, share none of the code”. This is why testing with hand-written fakes is so easy in Dart — no interface declaration required.

Mixins and linearisation

dart
mixin Logging {
  String get tag => runtimeType.toString();
  void log(String m) => print('[$tag] $m');
}

// `on` constrains what the mixin may be applied to and gives access to its API
mixin Retry on HttpClientBase {
  Future<Response> getWithRetry(String url, {int times = 3}) async {
    for (var i = 0; ; i++) {
      try { return await get(url); }              // get() comes from the `on` type
      catch (_) { if (i >= times - 1) rethrow; await Future.delayed(_backoff(i)); }
    }
  }
  Duration _backoff(int i) => Duration(milliseconds: 200 * (1 << i));
}

class Api extends HttpClientBase with Logging, Retry {}

// Resolution order (linearisation): rightmost mixin wins.
// Api  →  Retry  →  Logging  →  HttpClientBase  →  Object
// `super` inside a mixin refers to the *next type left* in that chain.
Interview follow-up

“If two mixins define the same method, which runs?” The one listed last in the with clause, because linearisation applies mixins left to right, each one sitting above the previous. Flutter uses this deliberately: RenderBox composes ContainerRenderObjectMixin, RenderBoxContainerDefaultsMixin and friends in a fixed order.

A mixin declaration cannot be instantiated or extended, has no constructor, and therefore cannot declare non-late final fields requiring construction. Use mixin class when a type must serve as both.

sealed class Result<T> {
  const Result();

final class Ok<T> extends Result<T> {
  final T value;
  const Ok(this.value);
}

  final Object error;
  final StackTrace stack;

// turns every switch in the codebase into a compile error. That is the point.

  Ok(value: final v)  => 'ok: $v',
  Err(error: final e) => 'failed: $e',
};
Library design rule

Publishing a plain class means anyone may implement its interface, so adding a method is a breaking change. If a type is an implementation you intend to evolve, mark it final or base. If it is a contract, mark it interface. This is the practical reason the modifiers exist.

noSuchMethod, covariant, and @override

dart

}

// noSuchMethod: last-resort dynamic dispatch (used by mocking libraries)
class LoggingProxy implements Api {
  @override dynamic noSuchMethod(Invocation i) {

  }

Generics & variance

Dart's generics are reified — type arguments exist at runtime, unlike Java's erasure — and covariant, which is convenient and slightly unsound. Both facts have observable consequences.

Reification

dart
final xs = <int>[];
print(xs is List<int>);      // true  — Dart keeps the type argument
print(xs is List<String>);   // false — impossible in Java

// You can therefore dispatch on a type argument
T decode<T>(String json) {
  if (T == User)  return User.fromJson(jsonDecode(json)) as T;
  if (T == Order) return Order.fromJson(jsonDecode(json)) as T;
  throw ArgumentError('no decoder for $T');
}

// And you can capture it
class TypeToken<T> { const TypeToken(); Type get type => T; }

Variance in practice

Dart generics are covariant: if Dog <: Animal then List<Dog> <: List<Animal>. That is sound for reading and unsound for writing, so the write is checked at runtime:

dart
List<Animal> animals = <Dog>[Dog()];   // allowed
animals.add(Cat());                     // compiles; throws TypeError at runtime

// The safe API design: accept the read-only supertype
double totalWeight(Iterable<Animal> xs) => xs.fold(0.0, (a, x) => a + x.weight);
// Callers can pass List<Dog>, Set<Cat>, or a lazy map() — and cannot mutate.
Interview follow-up

“How would you make a container that is safe to mutate?” Either take List<T> with T fixed by the caller, or expose Iterable<T> for reads and typed add/remove methods for writes. Note that Flutter uses covariance heavily and safely because widget trees are read-only after construction.

Bounds, extends, and self types

dart
// bounded: T must be comparable to itself
T maxOf<T extends Comparable<T>>(Iterable<T> xs) => xs.reduce((a, b) => a.compareTo(b) >= 0 ? a : b);

// F-bounded / self type — the copyWith and builder patterns
abstract class Entity<T extends Entity<T>> {
  String get id;

The classic bug

The event loop & Futures

Dart is single-threaded per isolate with two queues. Every async question — “why did this print out of order?”, “why did my UI freeze?”, “what's the difference between Future.microtask and Future(() {})?” — is answered by the same six-line model.

The model

┌──────────────── run main() to completion ────────────────┐ │ │ ▼ │ microtask queue ── drain COMPLETELY ──▶ empty? ──no──▶ loop back │ yes ▼ event queue ── take exactly ONE ──▶ run it ──▶ back to microtasks │ └── I/O, timers, gesture events, isolate messages, Future.then callbacks

Two rules follow, and they explain everything:

  1. The microtask queue is drained fully before any event is taken. An infinite microtask chain starves timers and I/O forever.
  2. Only one event runs per turn, so a long synchronous computation inside an event blocks the whole isolate — including Flutter's frame callbacks. That is jank.
dart · the ordering question
void main() {
  print('1 sync');

  Future(() => print('5 event queue'));                    // event queue
  Future.delayed(Duration.zero, () => print('6 timer'));   // timer → event queue
  Future.microtask(() => print('3 microtask'));            // microtask queue
  scheduleMicrotask(() => print('4 microtask'));           // microtask queue

  Future.value(42).then((v) => print('7 then on completed future'));

  print('2 sync');
}
// 1 sync
// 2 sync
// 3 microtask
// 4 microtask
// 7 then on completed future   ← .then on an ALREADY-completed future is a microtask
// 5 event queue
// 6 timer
Interview follow-up

“Why is 7 before 5?” Because Future.value is already complete, so its then callback is scheduled as a microtask, and microtasks jump the whole event queue. If the future were pending, the callback would run when the future completed — i.e. from the event queue.

async/await desugared

An async function runs synchronously up to its first await, then returns a Future to the caller and resumes later as a microtask. This surprises people constantly.

Future<T> retry<T>(Future<T> Function() body, {int attempts = 4}) async {
  for (var i = 0; ; i++) {
    try {
      return await body();
    } catch (e) {
      if (i >= attempts - 1 || !_isTransient(e)) rethrow;
      final ms = (200 * (1 << i)) + Random().nextInt(120);
      await Future.delayed(Duration(milliseconds: ms));
    }
  }

Future<List<R>> pool<T, R>(Iterable<T> items, Future<R> Function(T) f, {int limit = 6}) async {
  final results = <R>[];
  final queue = items.toList();
  Future<void> worker() async {
    while (queue.isNotEmpty) results.add(await f(queue.removeLast()));
  }
  await Future.wait(List.generate(limit, (_) => worker()));
  return results;
}

extension Debounce<T> on Stream<T> {
  Stream<T> debounce(Duration d) {
    Timer? timer;
    return transform(StreamTransformer<T, T>.fromHandlers(
      handleData: (event, sink) {
        timer?.cancel();
        timer = Timer(d, () => sink.add(event));
      },
      handleDone: (sink) { timer?.cancel(); sink.close(); },
    ));
  }

  Stream<T> throttle(Duration d) {
    DateTime? last;
    return where((_) {
      final now = DateTime.now();
      if (last == null || now.difference(last!) >= d) { last = now; return true; }
      return false;
    });
  }
}

Isolates & real parallelism

async gives you concurrency on one thread; isolates give you parallelism on many. Each isolate has its own heap and its own event loop, there is no shared mutable memory, and everything crosses the boundary as a message. This design is why Dart has no locks, no data races, and no volatile.

When you actually need one

WorkloadToolWhy
Network I/O, file I/O, databaseasync/awaitAlready off-thread in the platform; the isolate is idle while waiting
JSON parse > ~2 ms, image decode, crypto, compressionIsolate.run / computePure CPU — it would block the frame
Sustained background work (sync engine, log shipper)long-lived isolate + portsSpawning per task costs ~1 ms and a fresh heap
Many short CPU tasksisolate poolAmortise spawn cost

The easy path

The trap

The payload is copied (deep-copied for most objects, O(n)). Sending a 40 MB string to an isolate to save 8 ms of parsing can cost more than it saves. Measure. TransferableTypedData and SendPort with Uint8List can move bytes with zero copy in newer SDKs.

Long-lived isolates with ports

dart
class ThumbnailWorker {
  late final SendPort _tx;
  final _ready = Completer<void>();
  final _pending = <int, Completer<Uint8List>>{};
  var _seq = 0;

  Future<void> start() async {
    final rx = ReceivePort();
    await Isolate.spawn(_entry, rx.sendPort, debugName: 'thumbnails');
    rx.listen((msg) {
      if (msg is SendPort) { _tx = msg; _ready.complete(); return; }
      final (int id, Uint8List bytes) = msg as (int, Uint8List);
      _pending.remove(id)?.complete(bytes);
    });
    return _ready.future;
  }

  Future<Uint8List> resize(Uint8List src, int w) async {
    await _ready.future;
    final id = _seq++;
    final c = _pending[id] = Completer<Uint8List>();
    _tx.send((id, src, w));
    return c.future;
  }

  static void _entry(SendPort host) {
    final rx = ReceivePort();
    host.send(rx.sendPort);                    // handshake
    rx.listen((msg) {
      final (int id, Uint8List src, int w) = msg as (int, Uint8List, int);
      host.send((id, _resizeSync(src, w)));
    });
  }
}

What can cross an isolate boundary

  • Yes: null, num, bool, String, List/Map/Set of sendable values, records, TypedData, SendPort, Capability, and — since Dart 2.15 — most plain objects and closures by deep copy.
  • No: anything holding a native resource or a platform handle — open sockets, Socket, Isolate, most plugin objects, ReceivePort, and anything referencing a BuildContext.
  • Immutable objects and const values are shared, not copied — that is why String transfer is cheap in the VM but not on the web.
Interview follow-up

Errors, exceptions & failure design

Dart has unchecked exceptions only — nothing in the signature tells you what a function throws. That puts the burden on design: which failures are types, which are exceptions, and where the boundary sits.

Error versus Exception

Error
A programmer mistake. StateError, ArgumentError, RangeError, TypeError, UnimplementedError, AssertionError. Do not catch these — fix the code. Catching them hides bugs.
Exception
An expected, recoverable condition from the outside world. SocketException, FormatException, TimeoutException, and your own domain exceptions. Catch these.
anything
Dart lets you throw any object, including a String. Never do it — you lose stack-trace association and type-based catching.
dart
try {
  await repo.save(order);
} on SocketException catch (e) {
  // most specific first
  return Failure.offline(e.message);
} on ApiException catch (e, s) {
  if (e.status == 409) return Failure.conflict();
  log.error('save failed', e, s);
  rethrow;                       // rethrow preserves the ORIGINAL stack trace
} catch (e, s) {
  // catch-all with stack trace — never `catch (e)` alone in production code
  crash.record(e, s);
  throw UnexpectedFailure(e, s);
} finally {
  _spinner.hide();               // runs on success, throw, and return
}
throw e vs rethrow

throw e inside a catch block resets the stack trace to the current line, destroying the origin. Always rethrow. If you must wrap, pass the captured trace along: Error.throwWithStackTrace(wrapped, s).

Typed failures — the pattern seniors reach for

Exceptions are fine at the I/O boundary and poor as domain control flow, because the type system cannot see them. Convert once, at the repository edge, into a sealed result:

Extensions & extension types

Extensions add members to types you do not own, resolved statically. Extension types (Dart 3.3) go further: a compile-time-only wrapper with zero runtime cost, which is how you get type-safe IDs and JS interop without allocation.

Extension methods

  String get capitalised => isEmpty ? this : this[0].toUpperCase() + substring(1);
  String truncate(int n) => length <= n ? this : '${substring(0, n - 1)}…';
  int? get asIntOrNull => int.tryParse(this);

  TextTheme get text => Theme.of(this).textTheme;
  ColorScheme get colors => Theme.of(this).colorScheme;
  Size get screen => MediaQuery.sizeOf(this);
  EdgeInsets get safe => MediaQuery.paddingOf(this);

Static resolution

Extensions are resolved on the static type, not the runtime type. Calling an extension on a dynamic value fails at runtime with NoSuchMethodError, and an extension can never override a real member of the class — the instance member always wins. Two extensions defining the same member on the same type is an ambiguity error; disambiguate with StringX(s).isBlank or hide one on import.

Extension types — zero-cost wrappers

dart
// The classic bug this prevents: passing a UserId where an OrderId is expected.
extension type UserId(String value) {
  bool get isValid => value.startsWith('usr_');
}
extension type OrderId(String value) {}

void ship(OrderId id) {}
final u = UserId('usr_1');
// ship(u);            // COMPILE ERROR — exactly what we want
ship(OrderId('ord_9'));// fine

// At runtime both are just Strings: no allocation, no boxing.
print(u is String);    // true — it *is* the representation type

// Add `implements` to opt into the representation type's members
extension type Meters(double value) implements num {
  Meters operator +(Meters o) => Meters(value + o.value);
  String get label => '${value.toStringAsFixed(1)} m';
}
vs. a class wrapper
A final class UserId { final String value; } costs an allocation per instance and a dereference per read; an extension type costs nothing.
vs. a typedef
typedef UserId = String; is a pure alias — it provides no type safety at all. This is the distinction interviewers ask about.
caveat
Extension types are not real types at runtime: is/as see the representation type, and you cannot dispatch dynamically on them.

Memory, GC & leaks

Dart uses a generational, mostly-concurrent collector tuned for the allocation pattern Flutter creates: enormous numbers of very short-lived widget objects. Knowing the two-space design explains why allocating widgets every frame is fine and why holding one BuildContext too long is not.

The collector

GenerationAlgorithmCostWhat lives here
New space (scavenger)Semi-space copying (Cheney)Proportional to surviving objects only; typically < 1 msWidgets, closures, temporary lists — the 95% that die immediately
Old spaceMark–sweep, mostly concurrent; compacting mark–compact when fragmentedProportional to live set; runs concurrently with mutatorElements, RenderObjects, state, caches, images

Allocation in new space is a pointer bump. Because collection cost scales with survivors rather than garbage, creating a thousand throwaway widgets per frame is close to free — this is the design assumption that makes Flutter's rebuild-everything model viable. It also means the expensive thing is promotion: objects that survive a scavenge get copied to old space, so caching short-lived data is worse than recreating it.

The leak taxonomy in Flutter

1 · Undisposed controllers

AnimationController, TextEditingController, ScrollController, TabController, PageController, FocusNode. Each registers with a ticker or notifier list. Dispose in dispose().

2 · Live subscriptions

StreamSubscription, Timer, Ticker, addListener without removeListener. The listener closure holds this, which holds the whole element subtree.

3 · Captured BuildContext

Storing a BuildContext in a singleton, or awaiting then using context after the widget is gone. Guard with if (!mounted) return;.

4 · Unbounded caches

A Map keyed by user input with no eviction; ImageCache raised too high; keeping every page's state alive with AutomaticKeepAlive.

5 · Global mutable state

A static List of results appended per screen visit. Common in service-locator setups without scoping.

6 · Native memory

dart:ffi allocations, decoded images, platform-view textures. Invisible to Dart's heap graph — watch the OS RSS, not just DevTools' Dart heap.

The async-gap rule

After every await in a State method, either check mounted before touching context/setState, or capture what you need before the await (final nav = Navigator.of(context);). The use_build_context_synchronously lint enforces this; turn it on.

Finding leaks

  1. Open DevTools → Memory in profile mode. Take a heap snapshot.
  2. Navigate into the suspect screen and out again, several times. Force GC.
  3. Snapshot again and diff. If instance counts for your State classes grow with each visit, you have a leak.
  4. Select the class → inbound references → follow the retaining path to the root. The last non-framework object on that path is your bug.
  5. Add leak_tracker (built into flutter test) or package:leak_tracker_flutter_testing to catch regressions in CI.

dart
import 'dart:ffi';
import 'dart:io' show Platform;
import 'package:ffi/ffi.dart';    // calloc, toNativeUtf8

// 1. open the library — the path differs per platform
final DynamicLibrary _lib = switch (Platform.operatingSystem) {
  'android' => DynamicLibrary.open('libhash.so'),
  'ios' || 'macos' => DynamicLibrary.process(),      // statically linked into the app
  'windows' => DynamicLibrary.open('hash.dll'),
  _ => DynamicLibrary.open('libhash.so'),
};

// 2. describe the signature twice: native types, then Dart types
typedef _Fnv1aNative = Int32 Function(Pointer<Utf8>, Int32);
typedef _Fnv1aDart   = int   Function(Pointer<Utf8>, int);

final _fnv1a = _lib.lookupFunction<_Fnv1aNative, _Fnv1aDart>('fnv1a');

// 3. marshal, call, free — every allocation is yours to release
int hash(String s) {
  final p = s.toNativeUtf8();
  try {
    return _fnv1a(p, p.length);
  } finally {
    calloc.free(p);            // leak if you forget: not tracked by the GC
  }
}

// 4. structs
final class Vec2 extends Struct {
  @Float() external double x;
  @Float() external double y;
}

// 5. long native calls must not block the UI isolate
final result = await Isolate.run(() => hash(bigString));
FFI rules that bite
  • An FFI call is synchronous and blocking — a 30 ms native call is 30 ms of dropped frames. Wrap CPU-heavy calls in an isolate, or use @Native with isLeaf: true for tiny, fast calls.
  • Native memory is outside the GC: every calloc needs a free. Use package:ffi's using((arena) { ... }) for scoped allocation.
  • Callbacks from native into Dart must go through NativeCallable.listener (async, any thread) or NativeCallable.isolateLocal; a raw Pointer.fromFunction may only be invoked on the isolate's own thread.
  • Use ffigen to generate bindings from headers rather than hand-writing typedefs.

The three trees

If you learn one thing from this book, learn this chapter. The widget/element/render split is Flutter's central design decision and the source of nearly every non-obvious behaviour.

What each tree is for

Widget · configuration

@immutable. A description of what the UI should be. Cheap to allocate, thrown away every rebuild. Holds no state and knows nothing about the screen. Its only job is createElement().

Element · identity & lifecycle

Mutable, long-lived, one per position in the tree. Holds the State object, the BuildContext (an Element is the BuildContext), the parent/child links, and the dirty flag. This is the tree that persists across rebuilds.

RenderObject · geometry & pixels

Mutable, expensive. Performs layout (performLayout), painting (paint), and hit testing. Only created for widgets that draw or measure — RenderObjectWidget subclasses.

abstract class Widget {

}

  Widget get widget;

  void rebuild();                               // calls build(), diffs children
}

Reconciliation, step by step

When an Element rebuilds, it produces a new child widget and calls updateChild(oldChild, newWidget, slot). That single function is the diffing algorithm:

  1. newWidget == null → deactivate and unmount the old child subtree.
  2. oldChild == null → inflate the new widget: createElement() then mount.
  3. identical(oldChild.widget, newWidget) → return immediately. This is the const fast path from Chapter 03.
  4. Widget.canUpdate(oldChild.widget, newWidget) → same runtime type and same key: reuse the Element and its State, call update() with the new configuration, and recurse into children.
  5. Otherwise → unmount the old subtree entirely and inflate a new one. All State is lost, all controllers are disposed, all RenderObjects are discarded.
The question this answers

“Why did my TextField lose its text when I wrapped it in a Container?” Because the widget type at that position changed, step 5 fired, and the Element — with its State and TextEditingController — was destroyed. The fix is a GlobalKey, or hoisting the controller above the changing subtree.

Why not one tree?

Because the three have different cost profiles and different lifetimes. Widgets must be cheap enough to recreate 60–120 times a second. RenderObjects are expensive enough that recreating them would be impossible at that rate, so something must map “new configuration” onto “existing render object” — and that something needs stable identity, which is the Element. Separating them is what lets Flutter's declarative API sit on top of an imperative, retained render tree.

Keys & when you actually need them

Keys exist for exactly one reason: to tell the reconciler which old Element corresponds to which new widget when position alone is ambiguous. Every legitimate use of a key traces back to that sentence.

The taxonomy

The canonical demonstration

dart
// Two stateful colour tiles. Swapping them WITHOUT keys swaps nothing visible,
// because canUpdate() matches by (type, position) and the State stays put.
class _SwapDemoState extends State<SwapDemo> {
  var tiles = [
    const ColourTile(key: ValueKey('a')),   // remove the keys and the swap breaks
    const ColourTile(key: ValueKey('b')),
  ];

  void swap() => setState(() => tiles = tiles.reversed.toList());

  @override Widget build(BuildContext c) => Row(children: tiles);
}

Without keys: position 0 gets widget b, canUpdate returns true (same type, both keys null), so Element 0 keeps its State — the colour does not move. With keys: canUpdate returns false at each position, the framework searches the old child list for a matching key, finds it, and moves the Element (and its State, and its RenderObject) to the new slot.

Rules of thumb

  • Stateless children never need keys. There is no state to mismatch.
  • Stateful children in a reorderable/filterable/insertable list always need keys, and the key must be the domain identity (ValueKey(todo.id)), not the index.
  • Never ValueKey(index) in a mutable list — the index of an item changes when items are inserted above it, which is precisely the case keys are meant to survive.
  • Never UniqueKey() inside build of a list — every rebuild creates a new key, so every Element is destroyed and recreated every frame. This is a common and severe performance bug.
  • Put the key on the outermost widget of the subtree being moved, not on an inner child.

GlobalKey — power and cost

Costs and errors
  • A GlobalKey is registered in a global map; creating them in build churns that map every frame.
  • Duplicate GlobalKey detected in widget tree means the same key is mounted twice — usually the same widget rendered in two places, or an old subtree not yet unmounted during a transition.
  • Reparenting via GlobalKey forces a full layout of both the old and new location.
  • currentState/currentContext are null until the widget is mounted, so they are unusable in initState; use addPostFrameCallback.

The frame pipeline, end to end

This is the answer to “what happens between setState and a pixel changing”. Learn the eight phases and the two dirty lists, and you can reason about every performance problem Flutter has.

The eight phases of a frame

  1. vsync — the platform signals that a new frame is due. SchedulerBinding.handleBeginFrame runs.
  2. Transient callbacks — every Ticker, so all AnimationControllers advance and set their new values. This is where animations tick.
  3. Microtasks — drained.
  4. Persistent callbacks — drawFrame(): the rest of this list.
  5. Build — BuildOwner.buildScope sorts the dirty Element list by depth (shallowest first, so a parent's rebuild can subsume a child's) and calls rebuild() on each. Produces new widgets, reconciles, and may mark render objects dirty.
  6. Layout — PipelineOwner.flushLayout walks the _nodesNeedingLayout list, deepest relayout boundary first. Constraints go down, sizes come up.
  7. Compositing bits & Paint — flushCompositingBits, then flushPaint: each dirty repaint boundary records drawing commands into a Layer. Nothing is rasterised yet.
  8. Compositing & semantics — the layer tree is flattened into a Scene and handed to window.render(). flushSemantics updates the accessibility tree. The raster thread then executes the scene against the GPU.
Post-frame

WidgetsBinding.instance.addPostFrameCallback runs once, after phase 8, on the UI thread. It is the correct place to do anything that needs final geometry — measuring, showing a dialog triggered by initState, scrolling to an item.

dart · what setState really is
void setState(VoidCallback fn) {
  assert(fn != null);
  assert(_debugLifecycleState != _StateLifecycle.defunct);   // "called after dispose"
  final result = fn() as dynamic;
  assert(result is! Future, 'setState() callback must not be async');
  _element!.markNeedsBuild();     // ← that is the entire mechanism
}

// markNeedsBuild, simplified:
void markNeedsBuild() {
  if (_lifecycleState != _ElementLifecycle.active) return;
  if (dirty) return;                       // already scheduled — coalesced
  _dirty = true;
  owner!.scheduleBuildFor(this);           // adds to _dirtyElements
  // ... which calls SchedulerBinding.ensureVisualUpdate() → schedules a frame
}

Three consequences worth stating in an interview:

  • setState is not synchronous. It marks and returns; the rebuild happens later in the same frame. Reading a value you just set from a render object immediately afterwards gives you the old geometry.
  • Multiple setState calls in one turn coalesce into a single rebuild — the if (dirty) return; above.
  • setState during build throws. The dirty list is being drained in depth order; marking a shallower element would violate the ordering invariant. Hence “setState() or markNeedsBuild() called during build”.

Relayout and repaint boundaries

Layout does not always walk the whole tree. A RenderObject is a relayout boundary when its constraints are tight, or it is parentUsesSize == false, or it is a RenderAbstractViewport-style node — meaning its own size cannot change in response to a child change, so layout can stop there and restart from that node next time.

Full-marks answer

“Walk me from setState to a pixel.” — “setState mutates my state then calls markNeedsBuild, which flags this Element dirty and schedules a frame. At the next vsync, tickers advance animations, then the build phase rebuilds dirty Elements shallowest-first, reconciling new widgets against existing Elements by type and key. Reconciliation may mark render objects needing layout or paint. Layout runs from each dirty relayout boundary — constraints down, sizes up, single pass. Paint records display lists into layers per repaint boundary. The layer tree becomes a Scene, and the raster thread executes it via Impeller onto the GPU. Anything needing final geometry goes in a post-frame callback.”

Constraints: the layout algorithm

Flutter's layout is one pass, top-down for constraints and bottom-up for sizes, with the parent choosing the position. Nine words summarise it, and nearly every layout error is a violation of one of them: constraints go down, sizes go up, parent sets position.

BoxConstraints

dart
class BoxConstraints {
  final double minWidth, maxWidth, minHeight, maxHeight;
}
// Vocabulary an interviewer expects you to use precisely:
//   TIGHT       min == max on that axis      → the child has no choice
//   LOOSE       min == 0, max finite         → child picks up to max
//   UNBOUNDED   max == double.infinity       → child must size itself
//   EXPANDING   min == max == infinity       → illegal for most render boxes

const BoxConstraints.tight(Size(100, 50));
const BoxConstraints.loose(Size(100, 50));      // 0..100 × 0..50
const BoxConstraints.expand();                  // infinite × infinite
const BoxConstraints(minWidth: 200, maxWidth: 400, maxHeight: 80);

The child's rule is: pick the smallest size that satisfies the constraints and my own content. A widget cannot know its position, cannot know its siblings, and cannot exceed its constraints — if it tries, it is clipped and you get an overflow warning.

Flex layout, precisely

  1. Lay out every inflexible child (no Expanded/Flexible) with unbounded main-axis constraints; record their sizes.
  2. Subtract that total from the available main-axis extent → free space.
  3. Divide free space by the total flex → space per flex unit.
  4. Lay out each flexible child: Expanded gets a tight constraint of its share; Flexible gets loose up to its share.
  5. Position children according to mainAxisAlignment, then align each on the cross axis per crossAxisAlignment.

Writing a custom RenderObject

When neither composition nor CustomMultiChildLayout fits, drop to the rendering layer. Interviewers ask this to see whether you know the protocol.

dart · a "staircase" layout
class Staircase extends MultiChildRenderObjectWidget {
  const Staircase({super.key, required super.children, this.step = 24});
  final double step;

  @override RenderStaircase createRenderObject(BuildContext c) => RenderStaircase(step);
  @override void updateRenderObject(BuildContext c, RenderStaircase r) => r.step = step;
}

class _Data extends ContainerBoxParentData<RenderBox> {}

class RenderStaircase extends RenderBox
    with ContainerRenderObjectMixin<RenderBox, _Data>,
         RenderBoxContainerDefaultsMixin<RenderBox, _Data> {
  RenderStaircase(this._step);
  double _step;
  set step(double v) { if (v == _step) return; _step = v; markNeedsLayout(); }

  @override void setupParentData(RenderBox child) {
    if (child.parentData is! _Data) child.parentData = _Data();
  }

  @override void performLayout() {
    var dx = 0.0, dy = 0.0, width = 0.0;
    var child = firstChild;
    while (child != null) {
      child.layout(constraints.loosen(), parentUsesSize: true);   // constraints DOWN
      (child.parentData! as _Data).offset = Offset(dx, dy);       // parent sets POSITION
      dx += _step; dy += child.size.height;
      width = math.max(width, dx + child.size.width);
      child = childAfter(child);
    }
    size = constraints.constrain(Size(width, dy));                // size UP
  }

  @override void paint(PaintingContext context, Offset offset) =>
      defaultPaint(context, offset);
  @override bool hitTestChildren(BoxHitTestResult r, {required Offset position}) =>
      defaultHitTestChildren(r, position: position);
}

BuildContext & InheritedWidget

BuildContext is not a bag of services — it is the Element itself, exposed through a narrow interface. InheritedWidget is the framework's only built-in mechanism for O(1) dependency lookup, and every state-management library is built on it.

What a context can do

dart
// walks UP the tree, registers a dependency, rebuilds you when it changes
final theme = Theme.of(context);
final t = context.dependOnInheritedWidgetOfExactType<MyTheme>();

// finds it WITHOUT subscribing — safe in initState, will not rebuild you
final t2 = context.getInheritedWidgetOfExactType<MyTheme>();

// ancestor state — O(depth), no subscription; avoid in build
final scaffold = context.findAncestorStateOfType<ScaffoldState>();
final nav = context.findAncestorWidgetOfExactType<Navigator>();

// geometry — only valid after layout
final box = context.findRenderObject() as RenderBox?;
final size = context.size;

// walk down (debug/testing only — expensive and order-dependent)
context.visitChildElements((e) => print(e.widget));

// is this element still in the tree?
if (context.mounted) { ... }     // Flutter 3.7+: also State.mounted
Context pitfalls
  • Theme.of(context) inside a Builder-less Scaffold body sees the context above the widget you meant — wrap in a Builder to get a lower context.
  • Showing a SnackBar with the page's own context after that page was popped throws; capture ScaffoldMessenger.of(context) before the async gap.
  • findAncestorStateOfType is O(depth) and creates hidden coupling. Use it for framework interop, not architecture.
  • A context from initState cannot be used for dependOn…; dependencies are only registered during build/didChangeDependencies.

How InheritedWidget achieves O(1)

When an Element is mounted, it inherits its parent's _inheritedWidgets map — a Map<Type, InheritedElement>. An InheritedWidget ancestor adds itself to a copy of that map for its subtree. So dependOnInheritedWidgetOfExactType<T>() is a single hash lookup, not a tree walk, regardless of depth. The lookup also records the caller in the InheritedElement's dependent set, so a change can notify exactly the elements that read it.

dart · writing one
class AppConfig extends InheritedWidget {
  const AppConfig({super.key, required this.apiBase, required this.flags, required super.child});
  final String apiBase;
  final Set<String> flags;

  static AppConfig of(BuildContext context) {
    final c = context.dependOnInheritedWidgetOfExactType<AppConfig>();
    assert(c != null, 'No AppConfig found. Wrap your app in AppConfig(...).');
    return c!;
  }
  // the "maybeOf" convention for optional ancestors
  static AppConfig? maybeOf(BuildContext context) =>
      context.dependOnInheritedWidgetOfExactType<AppConfig>();

  // THE key method: return true only when dependents must rebuild
  @override
  bool updateShouldNotify(AppConfig old) =>
      apiBase != old.apiBase || !setEquals(flags, old.flags);
}
Interview follow-up

“What does updateShouldNotify control?” Whether every dependent element is marked dirty. Returning true unconditionally rebuilds the entire dependent set on every ancestor rebuild — a classic accidental-performance-cliff. Returning a precise comparison is why MediaQuery was split into MediaQuery.sizeOf, .paddingOf, .viewInsetsOf in Flutter 3.10: so a keyboard opening does not rebuild widgets that only read the size.

InheritedModel — aspect-based subscriptions

enum PrefAspect { theme, locale, fontScale }

}

Scrolling & slivers

Scrolling is where Flutter's performance model is most visible: lists must build lazily, recycle elements, and cooperate with a physics simulation. Slivers are the protocol that makes it possible.

Gestures & hit testing

Flutter resolves competing gestures with an arena: recognisers enter, one wins, the rest are rejected. Almost every “my tap doesn't work” bug is either a hit-test miss or a lost arena battle.

From pointer to callback

  1. The engine delivers a PointerDownEvent with a global position.
  2. GestureBinding.hitTest walks the render tree from the root, depth-first, building a hit-test path of every RenderObject whose hitTest returned true.
  3. Each RenderPointerListener on that path registers its recognisers in the gesture arena for that pointer.
  4. Subsequent move/up events are routed to the same path.
  5. A recogniser either claims victory (resolve(GestureDisposition.accepted)) — e.g. a drag exceeding kTouchSlop — or gives up. When only one remains, it wins and its callbacks fire.
  6. If nobody claims by the time the pointer is released, the arena picks the first registered member (the deepest widget wins, because hit-testing is depth-first).

Painting, clipping & custom graphics

Below the widget layer is a retained-mode canvas API. Custom painting is how you build charts, signatures, progress rings and anything the widget catalogue does not cover — and it is where raster-thread performance is won or lost.

CustomPainter

class GaugePainter extends CustomPainter {
  GaugePainter({required this.value, required this.track, required this.fill});
  final double value;            // 0..1
  final Color track, fill;

  @override
  void paint(Canvas canvas, Size size) {
    final centre = size.center(Offset.zero);
    final radius = size.shortestSide / 2 - 8;
    final rect = Rect.fromCircle(center: centre, radius: radius);

    // Allocate Paints here (cheap) but never build TextPainters per frame if avoidable.
    final base = Paint()
      ..color = track
      ..style = PaintingStyle.stroke
      ..strokeWidth = 12
      ..strokeCap = StrokeCap.round;

    final progress = Paint()
      ..shader = SweepGradient(
          startAngle: math.pi * 0.75,
          endAngle: math.pi * 2.25,
          colors: [fill.withValues(alpha: .5), fill])
        .createShader(rect)
      ..style = PaintingStyle.stroke
      ..strokeWidth = 12
      ..strokeCap = StrokeCap.round;

    canvas.drawArc(rect, math.pi * 0.75, math.pi * 1.5, false, base);
    canvas.drawArc(rect, math.pi * 0.75, math.pi * 1.5 * value, false, progress);

    final tp = TextPainter(
      text: TextSpan(text: '${(value * 100).round()}%',
          style: const TextStyle(fontSize: 22, fontWeight: FontWeight.w700)),
      textDirection: TextDirection.ltr,
    )..layout();
    tp.paint(canvas, centre - tp.size.center(Offset.zero));
  }

  // Called on every rebuild. Return false when nothing visual changed — this is
  // the difference between a smooth gauge and a repaint every frame.
  @override
  bool shouldRepaint(GaugePainter old) =>
      old.value != value || old.track != track || old.fill != fill;

  @override
  bool shouldRebuildSemantics(GaugePainter old) => false;

  @override
  SemanticsBuilderCallback? get semanticsBuilder => (size) => [
    CustomPainterSemantics(
      rect: Offset.zero & size,
      properties: SemanticsProperties(label: '${(value * 100).round()} percent', value: '$value'),
    ),
  ];
}

The animation system

Flutter's animations are values, not timelines. An Animation<T> is a listenable value plus a status; a Ticker advances it once per frame; everything else is composition.

The pieces

Ticker
Calls you back every vsync with the elapsed duration. Needs a TickerProvider (the SingleTickerProviderStateMixin/TickerProviderStateMixin on a State), which also mutes it when the route is off-screen.
AnimationController
A Ticker driving a value from 0→1 over a duration. It is an Animation<double> and a Listenable.
Curve
Remaps t∈[0,1] to t'∈[0,1]. Curves.easeOutCubic, Curves.elasticOut, Cubic(.2,0,0,1).
Tween<T>
Maps 0→1 onto begin→end for any type with lerp: ColorTween, RectTween, AlignmentTween, TweenSequence.
Animation<T>
The composed result: controller.drive(tween.chain(CurveTween(curve: c))).
Simulation
Physics instead of a duration: SpringSimulation, FrictionSimulation, GravitySimulation. Drive with controller.animateWith.

ref semantics — the part people get wrong

ref.watch
Subscribe. In build or in another provider. Re-runs the consumer when the value changes.
ref.read
One-shot, no subscription. Only in callbacks and event handlers. Using it in build means your UI silently stops updating.
ref.listen
Side effects on change: snackbars, navigation, analytics. Never watch for these.
ref.invalidate / refresh
Discard the cached value; refresh also returns the new one. Use for pull-to-refresh.
ref.keepAlive
Prevents auto-dispose until you close the link — the caching primitive.
ref.onDispose
Cleanup hook. This is where subscriptions and clients are closed.

BLoC in depth

BLoC's value is discipline: every change is an explicit event, every render is an explicit state, and the transition log is a complete audit trail. That is why regulated and large-team codebases favour it.

// Bloc: events in, states out. Choose it when you need event transformers
// (debounce/throttle/concurrency control) or a replayable event log.
class SearchBloc extends Bloc<SearchEvent, SearchState> {
  SearchBloc(this._api) : super(const SearchState.initial()) {
    on<QueryChanged>(
      _onQuery,
      transformer: (events, mapper) => events
          .debounce(const Duration(milliseconds: 300))
          .distinct()
          .switchMap(mapper),      // cancels the previous request — the correct choice
    );
    on<LoadMore>(_onLoadMore, transformer: droppable());
  }
  final Api _api;

  Future<void> _onQuery(QueryChanged e, Emitter<SearchState> emit) async {
    if (e.q.length < 2) return emit(const SearchState.initial());
    emit(const SearchState.loading());
    await emit.forEach<List<Hit>>(                    // handles cancellation for you
      _api.searchStream(e.q),
      onData: (hits) => SearchState.loaded(hits),
      onError: (e, s) => SearchState.failed('$e'),
    );
  }
}
concurrent()
all events processed in parallel (default for on without a transformer)
sequential()
queue; one at a time. Correct for writes that must not interleave.
droppable()
ignore new events while one is in flight. Correct for “load more” and double-tap protection.
restartable()
cancel the in-flight handler and start the new one. Correct for search.

BLoC anti-patterns
  • Mutable state objects. emit compares with ==; mutating the existing state and re-emitting it does nothing. Use freezed/records so state is immutable and value-equal.
  • A bloc calling another bloc. Blocs should not know about each other; put the coordination in a repository, or listen in the UI layer.
  • emit after the handler returns → StateError. Use emit.forEach/emit.onEach for stream-driven emission.
  • A state per widget. Blocs are per feature, not per button.

Dio buildClient(TokenStore tokens) {
  final dio = Dio(BaseOptions(
    baseUrl: Env.apiBase,
    connectTimeout: const Duration(seconds: 8),
    receiveTimeout: const Duration(seconds: 15),
    sendTimeout: const Duration(seconds: 15),
    headers: {'accept': 'application/json', 'x-client': 'flutter/${Env.version}'},
    validateStatus: (s) => s != null && s < 500,   // handle 4xx ourselves
  ));

  dio.interceptors.addAll([
    // 1. correlation id for tracing across services
    InterceptorsWrapper(onRequest: (o, h) {
      o.headers['x-request-id'] = const Uuid().v4();
      h.next(o);
    }),

    // 2. auth + single-flight refresh
    _AuthInterceptor(dio, tokens),

    // 3. retry idempotent requests only
    RetryInterceptor(
      dio: dio,
      retries: 3,
      retryDelays: const [Duration(milliseconds: 300), Duration(milliseconds: 900), Duration(seconds: 2)],
      retryEvaluator: (err, attempt) =>
          const {'GET', 'HEAD', 'PUT', 'DELETE'}.contains(err.requestOptions.method) &&
          (err.type == DioExceptionType.connectionError || (err.response?.statusCode ?? 0) >= 500),
    ),

    if (kDebugMode) LogInterceptor(requestBody: true, responseBody: true),
  ]);
  return dio;
}

class _AuthInterceptor extends QueuedInterceptor {
  _AuthInterceptor(this._dio, this._tokens);
  final Dio _dio; final TokenStore _tokens;
  Future<String>? _inFlightRefresh;      // ← the single-flight guard

  @override void onRequest(RequestOptions o, RequestInterceptorHandler h) {
    final t = _tokens.access;
    if (t != null) o.headers['authorization'] = 'Bearer $t';
    h.next(o);
  }

  @override Future<void> onError(DioException e, ErrorInterceptorHandler h) async {
    if (e.response?.statusCode != 401) return h.next(e);
    try {
      // Many parallel 401s must produce ONE refresh call, not N.
      final fresh = await (_inFlightRefresh ??= _refresh());
      final o = e.requestOptions..headers['authorization'] = 'Bearer $fresh';
      return h.resolve(await _dio.fetch(o));
    } catch (_) {
      _tokens.clear();
      authEvents.add(const SessionExpired());
      return h.next(e);
    } finally {
      _inFlightRefresh = null;
    }
  }
  Future<String> _refresh() async { /* POST /auth/refresh */ }
}

    onUpgrade: (m, from, to) async {
      if (from < 2) await m.addColumn(orders, orders.synced);
      if (from < 3) await m.createIndex(Index('idx_orders_placed', 'CREATE INDEX idx_orders_placed ON orders(placed_at DESC)'));
    },
    beforeOpen: (d) async => d.customStatement('PRAGMA foreign_keys = ON'),
  );

  // A reactive query: the stream re-emits whenever the underlying rows change.
  Stream<List<Order>> watchPending() =>
      (select(orders)..where((o) => o.synced.equals(false))
                     ..orderBy([(o) => OrderingTerm.desc(o.placedAt)])).watch();

  Future<void> upsertAll(List<Order> rows) =>
      batch((b) => b.insertAllOnConflictUpdate(orders, rows));   // one transaction
}
Offline-first in four rules
  1. The UI reads only from local storage, never directly from the network.
  2. Writes go to local storage immediately, marked synced: false, and are queued.
  3. A sync worker drains the queue with retries and reconciles server responses.
  4. Conflicts have a documented policy — last-write-wins with a server timestamp, or per-field merge, or explicit user resolution. Say which one and why.

class BatteryPlugin : FlutterPlugin, MethodCallHandler {
  private lateinit var channel: MethodChannel
  private lateinit var context: Context

  override fun onAttachedToEngine(binding: FlutterPlugin.FlutterPluginBinding) {
    context = binding.applicationContext
    channel = MethodChannel(binding.binaryMessenger, "acme/battery")
    channel.setMethodCallHandler(this)
  }

  override fun onMethodCall(call: MethodCall, result: Result) {
    when (call.method) {
      "getLevel" -> {
        val bm = context.getSystemService(Context.BATTERY_SERVICE) as BatteryManager
        val level = bm.getIntProperty(BatteryManager.BATTERY_PROPERTY_CAPACITY)
        if (level >= 0) result.success(level)
        else result.error("UNAVAILABLE", "Battery level not available", null)
      }
      else -> result.notImplemented()
    }
  }

  override fun onDetachedFromEngine(b: FlutterPlugin.FlutterPluginBinding) {
    channel.setMethodCallHandler(null)     // avoid leaking the engine
  }
}
Channel rules
  • Every call is async and crosses a thread. A tight loop of channel calls (per frame, per list row) is a performance disaster — batch instead.
  • Handlers run on the platform thread; long native work must be dispatched to a background executor or you cause an ANR.
  • The codec is untyped. A renamed method or a changed argument shape fails at runtime, on one platform, in production. This is exactly what Pigeon solves.
  • Result callbacks must be invoked on the main thread on Android and exactly once.

Performance engineering

Performance work is a measurement discipline. The only acceptable answer to “how would you fix this jank?” starts with which tool you open and which number you read.

The budget

At 60 Hz you have 16.67 ms per frame, split between the UI thread and the raster thread. At 120 Hz you have 8.3 ms. Anything over budget is a dropped frame. Profile mode only — debug mode is 2–10× slower and its numbers are meaningless.

Diagnosis by symptom

Raster thread over budgetsaveLayer: Opacity, ClipRRect, BackdropFilter, big shadowsDevTools → Raster track; remove layers, flatten into a painter

The optimisation checklist, in order of leverage

  1. Use lazy builders for every data-driven list/grid, with itemExtent when rows are uniform.
  2. Decode images at display size (cacheWidth/cacheHeight) and cache them on disk.
  3. Move setState down — split a big widget so only the changing leaf rebuilds. Free.
  4. Add const everywhere the analyzer allows; give your widgets const constructors.
  5. Hoist subtrees into the child parameter of AnimatedBuilder/ValueListenableBuilder so they build once.
  6. Delete layer-creating widgets you do not need; replace animated Opacity with FadeTransition or paint-level alpha.
  7. Move CPU work to an isolate — JSON over ~100 KB, image processing, crypto.
  8. Add RepaintBoundary around independently animating subtrees — but measure, because each one costs a layer.
  9. Defer non-critical startup work to addPostFrameCallback or a later frame.
  10. Only then consider architectural changes.
Interview answer template

“I reproduce it in profile mode on the slowest device we support, open the DevTools timeline, and look at which thread is over 16 ms. If it's the UI thread I expand the frame and find the widget with the largest build time — usually a non-lazy list or a rebuild too high in the tree. If it's the raster thread I turn on layer borders and look for saveLayer. I fix the single biggest contributor, re-measure, and repeat. I don't add RepaintBoundary or const speculatively without a before/after number.”

Architecture at scale

The question is never “what is clean architecture” but “how do you keep a 300-screen app from becoming unmaintainable”. The answer is enforced boundaries.

Layers, and the dependency rule

presentation widgets, controllers/blocs, view models │ depends on ↓ (never upward) domain entities, value objects, use cases, repository INTERFACES │ implemented by ↓ data repository IMPLEMENTATIONS, DTOs, API clients, DAOs │ infrastructure Dio, drift, secure storage, platform channels The domain layer imports NOTHING from Flutter. That is the test: if `flutter/material.dart` appears in domain/, the boundary has leaked.
text · feature-first structure that scales
apps/
  customer/                 # thin shell: main.dart, routing, DI composition, flavors
packages/
  core_ui/                  # design system: tokens, buttons, layout primitives
  core_network/             # Dio setup, interceptors, error mapping
  core_storage/             # drift database, secure storage wrappers
  core_analytics/
  feature_auth/
    lib/
      src/
        domain/    entities, use_cases, repository interfaces
        data/      dtos, mappers, repository impls
        presentation/  pages, widgets, controllers
      feature_auth.dart     # the ONLY public export — the module's API
  feature_catalogue/

How to enforce it
  • One package per feature; a feature may depend on core_* but never on another feature. Package boundaries make this a compile error, not a code-review comment.
  • Export exactly one barrel file per package; everything else under src/ is private by convention and by the implementation_imports lint.
  • Cross-feature navigation goes through the router (a string route or a typed route object), not by importing the other feature's page.
  • Cross-feature data goes through a core package or an event bus, not a direct dependency.
  • Use melos for bootstrapping, versioning and running tests across packages.

class PlaceOrder {
  const PlaceOrder(this._orders, this._inventory, this._analytics);
  final OrderRepository _orders; final InventoryService _inventory; final Analytics _analytics;

  Future<Result<Order>> call(Order draft) async {
    if (draft.lines.isEmpty) return const Err(ValidationFailed({'lines': 'empty'}));
    final stock = await _inventory.check(draft.lines);
    if (stock case Err(:final error)) return Err(error);
    final placed = await _orders.place(draft);
    if (placed case Ok(:final value)) _analytics.orderPlaced(value.id, value.total);
    return placed;
  }
}

class HttpOrderRepository implements OrderRepository {
  HttpOrderRepository(this._dio, this._dao);
  final Dio _dio; final OrderDao _dao;

  @override Stream<List<Order>> watchMine() =>
      _dao.watchAll().map((rows) => rows.map(OrderMapper.fromRow).toList());

  @override Future<Result<Order>> place(Order draft) async {
    await _dao.upsert(OrderMapper.toRow(draft, synced: false));   // offline-first
    try {
      final res = await _dio.post('/orders', data: OrderMapper.toJson(draft));
      final order = OrderMapper.fromJson(res.data);
      await _dao.upsert(OrderMapper.toRow(order, synced: true));
      return Ok(order);
    } on DioException catch (e) {
      return Err(FailureMapper.fromDio(e));      // ONE place converts transport → domain
    }
  }
}

Secrets

--dart-define values are compiled into the binary and are extractable by anyone with the APK. They are for endpoints and flags, never for API secrets. Anything genuinely secret belongs on your server behind an authenticated endpoint. Obfuscation raises the effort, not the guarantee.

Version strategy
version: 2.14.3+ + CI run number. Never bump by hand on a shared branch.
Staged rollout
internal → closed → 5% → 20% → 100%, with crash-free-rate gates between steps.
Symbol upload
Mandatory when using --obfuscate. Store build/symbols as a build artefact too.
Kill switches
Remote Config or your own flags endpoint, checked at launch, so a bad feature can be disabled without a store review.
Forced update
A minimum-supported-version check on launch; the app blocks with an update prompt. Design this before you need it.
Codepush
Dart code cannot be hot-updated on the app stores' terms; treat “over-the-air Dart updates” claims sceptically. Server-driven UI is the compliant alternative.
